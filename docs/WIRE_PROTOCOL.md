# 桩 ↔ 云 二进制帧协议（实现现状 + 待确认假设）

> 本文件描述 charging-pile ↔ cloud-service 之间 **TCP 长连接上的二进制帧**。
> 云 ↔ KGC 仍走 HTTPS + JSON（见附录 A.1），**不在本文范围**。
>
> ⚠️ 技术联络单的样例报文头是复制粘贴的（长度 `1C 00`、类型 `EB` 与实际对不上），
> 没有权威定义。以下**帧结构、字段表、校验/序列号/时间戳规则都是本次实现所做的假设**，
> 逐条列出，**待与对方确认**。确认前请勿视为最终规范。

## 1. 帧结构（假设 F1–F7）

```
偏移  字段          长度  说明
0     起始符        1     固定 0x68
1     数据长度      2     大端；= 载荷字节数（不含帧头/帧尾）           [假设 F1]
3     序列号        2     大端；每个端点自己的发送计数器，从 1 递增     [假设 F5]
5     加密标志      1     0x00=明文；协商阶段一律 0x00                  [假设 F4]
6     类型          1     0x39/0x3A/0x3B/0x3C（见 §2）
7     主机编号      7     BCD，充电桩编号；云→桩帧也填桩编号            [假设 F6]
14    载荷          N     按 §2 各报文字段表顺序，全定长直拼
14+N  帧校验        2     大端 CRC-16/CCITT-FALSE，范围 [0 .. 14+N-1]   [假设 F2]
```
整帧长度 = 16 + N。

- **[F1]** 数据长度只覆盖**载荷**，不含 16 字节帧头尾。（联络单未定义覆盖范围。）
- **[F2]** 帧校验算法假设为 **CRC-16/CCITT-FALSE**（poly=0x1021, init=0xFFFF, 不反转, xorout=0），
  覆盖从起始符 0x68 到载荷末字节的所有字节。**联络单未定义校验算法**——这是纯假设。
- **[F3]** 多字节整数一律**大端**。
- **[F4]** 加密标志：协商阶段报文本身不加密，置 0x00。会话密钥启用后的应用数据通道加密**未实现**。
- **[F5]** 序列号：发送方每发一帧自增（从 1），**接收方目前只记录、不校验、不用于重传**。
  “序列号如何用于去重/重传/乱序” **未定义**。
- **[F6]** 主机编号 7 字节 BCD：由桩配置 `pile.id` 中的**数字字符**提取、右对齐、左补 0 得到 14 位十进制再 BCD。
  例：`pile-001` → 数字 `001` → `0000000000001` → `00 00 00 00 00 00 01`。
  **这是传输/路由字段，不参与任何密码学计算**；密码学用的 ID 是带内 ASCII 串（见 §3）。
- **[F7]** 未使用字段按“全 F”约定填 `0xFF`（本实现的字段表中暂无未使用字段）。

## 2. 报文类型与步骤号（Part C：消歧方案）

联络单同一“轮次”下有发起/回执多条语义不同的报文，靠“哪些字段全 F”区分不可靠。
**本实现在每条报文载荷首部之外，用类型 + 1 字节步骤号唯一确定语义**：

- **类型字节**给出阶段与方向：`0x39`=一阶段 桩→云，`0x3A`=一阶段 云→桩，
  `0x3B`=二阶段 桩→云，`0x3C`=二阶段 云→桩。
- **步骤号 STEP**（载荷第 1 字节）= `高4位=轮次 | 低4位=类别`，类别 `1=请求/发起`、`2=应答/回执`。
  于是 `(类型, STEP)` 组合全局唯一。

### 第一阶段（provision，双向 HMAC-SM3 + 申请部分私钥）
| 类型 | STEP | 名称           | 载荷（STEP 之后，全定长直拼） |
|------|------|----------------|------------------------------|
| 0x39 | 0x11 | hmac_req       | ID_B(32) ‖ UA(64) ‖ randomB(16) |
| 0x3A | 0x12 | hmac_challenge | ID_A(32) ‖ mac_B(32) ‖ randomA(16) |
| 0x39 | 0x21 | hmac_response  | mac_A(32) |
| 0x3A | 0x22 | auth_result    | result(1) ‖ ID_A(32) |
| 0x39 | 0x31 | pk_request     | ID_B(32) ‖ UA(64) |
| 0x3A | 0x32 | pk_response    | WA(64) ‖ partialPrivate(129) ‖ Ppub(64) |

- `mac_B = HMAC-SM3(PSK, randomB)`（云自证）；`mac_A = HMAC-SM3(PSK, randomA)`（桩自证）。
- `result`：0x00=通过，0x01=失败。桩必须校验 `mac_B`，云必须校验 `mac_A`，任一失败即中止。

### 第二阶段（session，两步协商 + 双向回执）
| 类型 | STEP | 名称        | 载荷（STEP 之后） |
|------|------|-------------|-------------------|
| 0x3B | 0x11 | ka_request  | UUID(32) ‖ CP56(7) ‖ ID_B(32) ‖ WB(64) ‖ rB(64) ‖ nonce(16) ‖ sig_B(64) |
| 0x3C | 0x12 | ka_response | UUID(32) ‖ CP56(7) ‖ result(1) ‖ ID_A(32) ‖ WA(64) ‖ rA(64) ‖ sig_A(64) |
| 0x3B | 0x21 | ka_confirm  | UUID(32) ‖ CP56(7) ‖ result(1) ‖ received(1) |
| 0x3C | 0x22 | ka_ack      | UUID(32) ‖ CP56(7) ‖ received(1) |

- `result` in `ka_response` = 云对桩签名 `sig_B` 的**验签结果**（0x00 通过 / 0x01 失败）。
- `result` in `ka_confirm` = 桩对云签名 `sig_A` 的**验签结果**；`received=0x01` 表示“已收到 ka_response”。
- `ka_ack.received=0x01` = 云确认“已收到桩的 ka_confirm”。这实现了联络单“验签结果 + 是否收到”的回执来回。

## 3. 密码学字段的编码（沿用既有实现，未改算法）

- **ID_A/ID_B（密码学用）**：ASCII 串右侧 0x00 补齐到 **32 字节**（`cloud-001`/`pile-001`）。
  transcript、会话密钥 KDF、HA(算 λ)、SM2 签名 ZA **四处统一 32 字节**（本轮 Part A 已统一）。
  ⚠️ 与帧头 **7 字节 BCD 主机编号是两回事**：带内 ASCII 才是密码学身份，BCD 仅传输层用。
- **nonce**：线上 16 原始字节；参与 transcript/KDF 时用其 **32 字符小写 hex 的 ASCII 字节**（密码学逻辑未改）。
- **randomA/randomB**：线上 16 原始字节；HMAC 输入用其 hex。
- **点（UA/WA/WB/rA/rB/Ppub）**：64 字节裸 `X‖Y`（无 04 前缀）。
- **签名 sig_A/sig_B**：64 字节裸 `r‖s`。
- **partialPrivate**：SM2 密文 C1C3C2（C1 含 04），129 字节。
- **CP56Time2a**：7 字节标准格式（毫秒 2 + 分 1 + 时 1 + 日 1 + 月 1 + 年 1）。**当前为传输元数据，不参与签名**。 [假设 T1]
- **UUID**：32 字节 ASCII，桩在 `ka_request` 随机生成，后续帧回填做会话关联。**不参与签名**。 [假设 U1]

- **[T1/U1]** 联络单未定义 CP56Time2a / UUID 是否纳入签名 transcript。本实现**不纳入**（仅传输元数据）。
  若需绑定防重放，需要双方同时把它们加入 transcript——**待确认**。

## 4. 已知未实现 / 仍未定义（需对方拍板，勿自行决定）

1. **帧校验算法**：假设 CRC-16/CCITT-FALSE（F2）。联络单未给算法。
2. **序列号语义**：仅自增+记录（F5）。去重/乱序/重传窗口未定义。
3. **超时重传**：无。当前任一步读超时即断开中止，无重传。
4. **协商失败重试策略**：无。桩失败即退出（一阶段失败不落 keystore；二阶段失败不派生 SK）。
5. **会话密钥切换启用时机**：SK 派生后仅用于打指纹日志，**没有**切换成应用数据加密通道；
   SK(32B)→SM4 密钥(16B) 的取用规则**双方都缺**。
6. **加密标志位的后续用途**：加密数据通道未实现（F4）。
7. **CP56Time2a / UUID 是否纳入签名**：当前不纳入（T1/U1）。
8. **主机编号 BCD 与 ASCII 身份的关系**：BCD 仅传输层、ASCII 才是密码学身份（F6）；
   若现网要求 BCD 即身份，则 transcript/KDF/HA/ZA 全部要改，会破坏当前互通。
