## 甲、算法正文的空缺与错误（10 条）

### 甲-1　会话密钥公式空缺

| 项 | 内容 |
|---|---|
| 联络单现状 | 会话密钥的计算公式为空 |
| 实际实现 | 单次 SM3，输入共 240 字节，输出 32 字节 |
| **建议改为** | 见下方公式 |

```
SK = SM3( Sx(32) ‖ R_A(64) ‖ R_B(64) ‖ ID_A(32) ‖ ID_B(32) ‖ nonce(16) )
```

- `Sx`：本方临时私钥 × 对端临时公钥 所得点的 **X 坐标**，32 字节大端定长
- 字段按顺序**直接拼接**，无长度前缀、无分隔符
- **单次 SM3**，无计数器、无迭代
- 输出 32 字节会话密钥
- 双方各用自己的临时私钥与对方的临时公钥计算，得到相同 `Sx`，因而得到相同 `SK`

### 甲-2　λ 与 HA 的算法未写

| 项 | 内容 |
|---|---|
| 联络单现状 | 隐式证书的 `HA`、`λ` 计算方式未定义 |
| 实际实现 | 见下方公式 |
| **建议改为** | 补入正文，并同时给出曲线参数 `a`/`b`/`Gx`/`Gy` 取值（实现方计算 `HA` 必需） |

```
HA = SM3( 0x0100 ‖ ID(32) ‖ a ‖ b ‖ Gx ‖ Gy ‖ Ppub.x ‖ Ppub.y )
λ  = SM3( W.x ‖ W.y ‖ HA )
PK = W + λ·Ppub
SK = (d + t) mod n        // d 为本机私钥，t 为解密出的部分私钥
```

- `0x0100` 为 ENTL（ID 恒为 32 字节 = 256 bit），大端两字节
- `Ppub.x`/`Ppub.y`/`W.x`/`W.y` 均为 32 字节大端
- `λ` 为 SM3 输出的 32 字节，按**大端无符号整数**用作标量（点乘按群阶归约，是否显式 `mod n` 不影响结果）
- 自洽关系：`SK·G == PK`

### 甲-3　nonce 参与拼接的字节形态未写

| 项 | 内容 |
|---|---|
| 联络单现状 | 未说明 nonce 参与哈希时的字节形态 |
| 实际实现 | 在 transcript、会话密钥派生、HMAC **三处一律使用解码后的 16 原始字节** |
| **建议改为** | 明确写「**解码后的 16 原始字节**」，避免被理解成 32 字符的 hex 文本 |

> 这是最容易产生跨端不一致的点：若一端用 16 原始字节、另一端用 32 个 hex 字符，
> 签名与会话密钥都会不同，且不会有任何报错，只表现为验签失败。

### 甲-4　编码总则缺失

| 项 | 内容 |
|---|---|
| 联络单现状 | 未规定进哈希/签名字段的字节表示 |
| 实际实现 | 一律使用「hex 解码后的原始字节」 |
| **建议改为** | 作为**总则**写在正文开头 |

> **总则：所有进入哈希 / 签名的字段，一律使用「解码后的原始字节」，绝不使用 hex 文本本身。**
> hex 只是配置与接口的传参形式。

各字段进哈希时的字节数：

| 字段 | 字节数 |
|---|---|
| 曲线点（`R_A`/`R_B`/`W`/`Ppub`/`PK`） | 64 |
| `ID_A` / `ID_B` | 32 |
| `nonce` | 16 |
| `Sx` | 32 |
| 签名 `r` / `s` | 各 32 |

### 甲-5　ID 编码只提了一种

| 项 | 内容 |
|---|---|
| 联络单现状 | 只描述了一种 ID 编码场景 |
| 实际实现 | 同一个 32 字节 ID 用于 **HA、SM2 的 ZA、transcript、会话密钥派生** 四处，不做任何变形 |
| **建议改为** | 写清「四处统一」，并写明 `ENTL` 取值 |

- ID 恒为 **32 字节**
- 因 ID 定长 32 字节，SM2 的 **ENTL 恒为 `0x0100`**（256 bit，大端两字节）
- 线上报文与 KGC HTTP 接口的 `id` 字段一律传 **64 字符 hex**，收到后解码成 32 字节直接进密码学层

### 甲-6　主机编号「不足 7 位补 0」含糊

| 项 | 内容 |
|---|---|
| 联络单现状 | 「不足 7 位补 0」，未说明补在左侧还是右侧 |
| 实际实现 | 十进制字符串**左侧补 `'0'`** 到 14 位，再每 2 位压成 1 字节 BCD |
| **建议改为** | 按下方规则写死，并附字节级示例 |

**规则**：主机编号为十进制数字串（1..14 位）。不足 14 位时**在左侧补 `'0'`** 补足 14 位
（保持数值不变），再每 2 个十进制位压成 1 字节 BCD（高半字节为前一位数字），得 7 字节。

```
主机编号 "1"（等价于 "00000000000001"）
  → 左补零：00000000000001
  → BCD ：  00 00 00 00 00 00 01
  → ID_B ： 00 00 00 00 00 00 01 | 00 × 25
```

> 若改为右侧补零，`1` 会变成 `10000000000000`（数值放大 10^13 倍），故必须明确为左补。
> 超过 14 位或含非十进制字符应直接报错，不得截断。

### 甲-7　`H_MAC256` 与 `hmac_sm3_hex` 自相矛盾

| 项 | 内容 |
|---|---|
| 联络单现状 | 正文写 `H_MAC256`，附录写 `hmac_sm3_hex`，两处矛盾 |
| 实际实现 | **HMAC-SM3**（C++ `HMAC(EVP_sm3(), …)`；Java `new HMac(new SM3Digest())`），输出 32 字节 |
| **建议改为** | 正文统一改为 **HMAC-SM3**，删除 `H_MAC256` 字样 |

- 底层哈希为 **SM3**，不是 SHA-256
- 输出 **32 字节**
- 第一阶段挑战值 `random_A` / `random_B` 各 **16 字节**，参与 HMAC 的是这 16 个原始字节

### 甲-8　SM4 密钥取用规则未定义

| 项 | 内容 |
|---|---|
| 联络单现状 | 未定义如何从 32 字节会话密钥得到 16 字节 SM4 密钥 |
| 实际实现 | 取会话密钥 `SK` 的**前 16 字节** |
| **建议改为** | **SM4 密钥 = 会话密钥 `SK` 的前 16 字节** |

### 甲-9　曲线点长度与 C1 例外

| 项 | 内容 |
|---|---|
| 联络单现状 | 若正文只写「点为 64 字节」，则与 129 字节的密文长度对不上 |
| 实际实现 | 线上点一律 **64 字节裸 `X‖Y`（不含 `04`）**；**唯一例外**是 SM2 密文中的 `C1` 含 `04`（65 字节） |
| **建议改为** | 补一句 C1 例外说明 |

- 所有线上传输的公钥点：**64 字节裸 `X‖Y`**，128 hex，**不含 `04` 前缀**
- **例外**：SM2 密文内部的 `C1` 为 SEC1 非压缩格式，**含 `04`，共 65 字节**（GM/T 0003 标准要求）
- 65 字节 SEC1 仅在构造密文与调用底层库时出现，不作为线上点格式

### 甲-10　SM2 密文结构未写全

| 项 | 内容 |
|---|---|
| 联络单现状 | 未完整说明部分私钥密文的结构与校验要求 |
| 实际实现 | C1C3C2 原始拼接，共 129 字节；解密须校验 C3 |
| **建议改为** | 补入结构与 C3 校验要求 |

```
密文 = C1(65，含 04) ‖ C3(32) ‖ C2(与明文等长)
部分私钥明文为 32 字节 ⇒ 密文共 129 字节（258 hex）
```

解密流程（GM/T 0003）：

1. `S = d · C1`，取 `S` 的 `x2 ‖ y2`
2. `t = KDF(x2 ‖ y2, len(C2))`，KDF 计数器从 **1** 开始，每轮取 `SM3(x2 ‖ y2 ‖ ct_be32)`
3. 明文 `M = C2 XOR t`
4. **校验 `C3 == SM3(x2 ‖ M ‖ y2)`**，不符即解密失败

> 影响面：若选 ②，桩端与云端都需增加一轮收发与状态处理。

### 乙-12　轮次歧义（建议加显式步骤号）

| 项 | 内容 |
|---|---|
| 联络单现状 | 同一「轮次」下存在多条语义不同的报文（发起 / 回执），靠「哪些字段填全 F」来区分 |
| 问题 | 该方式无法可靠实现：接收方需先猜测语义才能解析，且新增字段会改变判定结果 |
| **建议改为** | **增加显式步骤号字段**，使每条报文语义唯一 |

**建议方案**：报文类型字节给出「阶段 + 方向」，载荷首字节放 1 字节步骤号
`STEP = 高 4 位（轮次） | 低 4 位（类别：1=请求/发起，2=应答/回执）`，
使 `(类型, STEP)` 组合在全协议内唯一。

> 说明：当前实现的桩↔云链路为 JSON 演示封装，用 `type` 字段区分语义，不存在此歧义；
> 本条针对的是联络单中的二进制报文方案。

|---|---|

| 实际实现 | 桩↔云当前为 JSON 演示封装，**未实现二进制帧** |
| **待拍板** | 是否落地二进制帧。若落地，下列各项必须先在联络单中定义 |

| 待定义项 | 说明 |
|---|---|
| 帧校验算法 | CRC 类型与多项式、覆盖范围（是否含帧头/帧尾） |
| 数据长度字段 | 覆盖范围（仅载荷，还是含帧头） |
| 序列号语义 | 是否用于去重、乱序处理、重传窗口、回绕规则 |

| 加密标志位 | 置位后的具体加密方式与作用范围 |

## 六、待对方明确的项

### ID 参数的命名统一

A.3 中 ID 参数在不同函数里写法不一：`sign_initiator` 写作 `id`，而 `reconstruct_full_public`
一侧目前实现为 `id_hex`。两者承载的都是**同一个 32 字节 ID 的 64 字符 hex**，仅命名不同。

| 函数 | 当前 ID 参数名 |
|---|---|
| `sign_initiator` / `verify_responder` / `verify_initiator` | `id` |
| `reconstruct_full_public` / `verify_keypair_consistency` | `id_hex` |

建议二者统一（推荐统一为 `id_hex`，与其它 hex 入参的命名风格一致），请对方确认后一并修订
联络单与 SDK。此项**不影响任何功能与线上格式**，纯命名。
